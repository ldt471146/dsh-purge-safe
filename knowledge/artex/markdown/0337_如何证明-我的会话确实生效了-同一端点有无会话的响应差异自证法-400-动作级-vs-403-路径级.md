· **无会话** → `200 {"challengeId":"i_yj_...","expiresIn":120}`
· **带有效会话**（`X-Session-Id` + `Authorization: Bearer <accessToken>`）→ `400 {"error":"request_rejected","code":"INVALID_INPUT"}`
⇒ **同一个端点、同一个 body，响应码从 200 变成 400 动作级错误码 ⇒ 证明"会话确实被服务端处理并改变了行为"**。
用途实证：据此判定 `auth/verification/{send,verify,status,cancel}` 的 `403 REQUEST_REJECTED` 是**路径级**（路由白名单）而非"缺会话" —— 因为同一批请求里既有 400（动作级）也有 403（路径级），两者闸的位置不同 ⇒ 结案结论可复核（见 vuln 67）。
★ 配套技巧：若目标端点在带会话时**没有**任何行为差异，就换一个"已知会因登录态而变"的端点做对照（本次是 password/start），否则无法区分"接口本来就这样"与"会话没生效"。

## 描述

测试手法：用"同一端点在有/无会话下的响应差异"自证会话是否真的生效，专门用来排除"会话没带上/没生效"造成的假阴性。本次实战中它把一条结论从"不可达"救成了"可复核的不可达"。

## 用法

```
# 场景：你打某个端点回 403/404，怀疑是"没带会话"，还是"根本没权限/不存在"？
# 做法：找一个【已知会因登录态而改变响应】的端点做对照，一次请求就能定性。
#
# 本战役的具体用法（v27）：
#   对照端点 = POST /IMService/v27/auth/password/start   body={"username":"<你的授权账号>","publicKey":"<SPKI>"}
#       无会话 -> 200 {"challengeId":...}          # 正常受理
#       带会话 -> 400 {"code":"INVALID_INPUT"}     # ★ 动作级错误码 ⇒ 会话生效
#   待测端点 = POST /IMService/v27/auth/verification/send
#       无会话 -> 403 REQUEST_REJECTED
#       带会话 -> 403 REQUEST_REJECTED             # ★ 路径级 ⇒ 不是"缺会话"，是路由白名单挡住
#   ⇒ 两条响应的"错误码层级"不同（400 动作级 / 403 路径级）⇒ 结论可信
#
# 错误码分级速查（本靶标实测）：
#   404 REQUEST_REJECTED            = 路径不在白名单 / 动作未知（路径级）
#   403 REQUEST_REJECTED            = 路径不在白名单（路径级；注意与上同码不同位）
#   400 INVALID_INPUT/MISSING_FIELD/UNKNOWN_FIELD/invalid_*  = 动作存在，载荷不对（动作级）
#   403 xxx_DENIED / ROOM_ROLE_REQUIRED / forum_speaking_eligibility = 动作存在但有闸
#   404 xxx_not_found               = 动作存在，对象不存在
#   401 AUTHENTICATION_REQUIRED     = 动作存在，但无会话（会话闸有效）
#   200                             = 真通（仍须按"假成功四板斧"复验）
```
