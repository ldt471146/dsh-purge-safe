## 描述

★ 老 Java servlet「读写判别」的完整五步法。**由两条独立踩坑经验合成**（写侧由本靶标实测、读侧由同战役另一路补上 —— 两条坑正好互补，缺任一条都会得出相反结论）。

**背景**：这类系统上，**两个不同测试者对同一个 servlet 会得出完全相反的结论**（"能写"/"不能写"、"可复现"/"不可复现"）。根源是两个坑：

**坑 A（写侧 —— 写入分支依赖"看似无关的参数"在场）**
老 servlet 常见写法：
```java
int flag = Integer.parseInt(getParameter("flag"));    // 缺参即 NumberFormatException
if (flag == 1) { /* 写入分支 */ }
else if (flag == 3) { /* 切换分支，需会话 */ }
```
只发 `userid=1` 会掉进**报错分支**（回 `-数据异常` / 500），于是被判"不可写"；**带上那个"看似无关"的参数**（`flag`/`type`）后，才走进真正的写入分支。
**⇒ 教训：单参数探测得出的"否定"结论不可靠，必须先把"最小必需参数集"补齐。**

**坑 B（读侧 —— 缓存窗口内的"写后读回"会命中旧值）**
读接口若走 Redis 缓存（本例 `/LHService/userinfo` 回 `source: LEGACY_REDIS`），则**写入后短时间内的读回会命中旧值** ⇒ 会把**真写误判成假写**。
**★ 而且常规的缓存击穿参数（`_=<ts>`、`t=<ts>`、`?rand=`）在这个实现里无效**（实测）。
**⇒ 教训：跨时间窗多次读回，别在同一秒内判定。**

**★ 五步判据（合起来才完整）**
| 步 | 动作 | 判据 |
|---|---|---|
| ① | **纯读稳定性检验** | 同一请求连发几次，看响应是否逐字节一致（不一致 ⇒ 有缓存/动态） |
| ② | **裸请求 vs 戴参数钥匙串 对照** | 裸请求 500/NPE vs 戴钥匙 200 ⇒ 存在"int 参数门槛"，必须补齐参数 |
| ③ | **逐个剔除法定最小必需集**（或用二分，O(log n)） | 收敛到几个参数即真正的入参面 |
| ④ | **写后跨时间窗多次读回**（≥30s 后再读一次） | 两次读回都变 ⇒ 真写；都未变 ⇒ 假写 |
| ⑤ | **值域枚举时用「文案推进」作判据，不要用「限流触发」作判据** | 见下 |

**★ 坑 C（值域枚举的判据陷阱 —— 本靶标实测踩出来的新坑）**
枚举 `flag` 值域时，我曾看到 `flag=6` 回「-操作过于频繁，请稍后再试」而判它"是唯一真登录分支"。
**这是错的**：判别实验（同一 flag 连打 10 发 × 2 个不同账号，共 20 发）显示**零限流**，而原探测是**同一个账号连打 18 发**、在第 15~17 发才触发。
**⇒ 限流是按「账号/客户端」计数（本例阈值约 12~15 次/窗口、计数键 = `(servlet 路径, 账号参数值)`），与业务分支无关。**
**⇒ 正确判据：看「文案是否推进到新的语义」（如从 `-请填写密码` 推进到 `-请使用手机号验证码登录`），而不是看是否被限流。**
**⇒ 红线：值域枚举务必每个探针换一个假账号**，否则会打满真实账号的桶，把唯一的活登录口锁死。

**★ 组合口诀**
> **参数要补齐（防假否定）· 读回要跨窗（防假否定）· 值域看文案（防假肯定）· 探针换假号（防锁桶）**

**判据对照表（老 servlet 文案 → 语义）**
| 文案 | 语义 |
|---|---|
| 500 `NumberFormatException` + 行号 | 有 int 参数门槛未满足；行号可用于"参数发现 oracle" |
| `-请填写登陆账号` | 缺账号参数（该文案即账号参数名的 oracle） |
| `-请填写密码` | 账号已识别，缺密码参数（⇒ 验证码不走该字段） |
| `-数据异常` | 进了业务分支但数据不对（登录尝试分支，**与 flag 取值无关**） |
| `-请重新登录` | 需已有会话（**不是** ID-only 绕过） |
| **`-操作过于频繁`** | **★ 不可用作分支判据** —— 它只反映账号级计数，与分支无关 |
| 200 + 空 body（len=0） | 参数不全、代码提前 return，**未执行** |

## 用法

```
```python
# ① 纯读稳定性检验：同一请求连发 3 次，看是否逐字节一致
b = [txt(GET(url)) for _ in range(3)]
print("纯读稳定" if len(set(b)) == 1 else "★ 有缓存/动态 ⇒ 后续读回必须跨时间窗")

# ② 裸请求 vs 戴参数钥匙串 对照（老 servlet 的 int 参数门槛）
r_bare = GET(url); r_key = GET(url + "?" + PARAM_KEY_QS)
print("裸=%s/%d  钥匙=%s/%d" % (r_bare["status"], len(r_bare["body"]),
                                r_key["status"], len(r_key["body"])))

# ③ 逐个剔除法定最小必需集（或用二分，O(log n)）
need = [x for x in PARAM_KEY_QS.split("&") if x]
i = 0
while i < len(need) and len(need) > 1:
    t = need[:i] + need[i+1:]
    if ok(GET(url + "?" + "&".join(t))): need = t
    else: i += 1
print("最小必需集:", [x.split("=")[0] for x in need])

# ④ ★ 写后跨时间窗多次读回（防缓存把真写判成假写）
WRITE(url, marker_body)                  # 打写入
t0 = READ(url)                           # 立刻读
time.sleep(35)                           # ★ 必须等
t1 = READ(url)                           # 跨窗再读
print("真写" if (MARKER in t0 and MARKER in t1) else
      "假写(两次都没标记)" if (MARKER not in t0 and MARKER not in t1) else
      "★ 缓存假否定(立刻读无、跨窗读有)")

# ⑤ 值域枚举：看文案推进，不看限流
for v in VALUES:
    m = txt(POST(url, "flag=%s&username=%s" % (v, NEW_FAKE_ACCT())))   # ★ 每个探针换假号
    print("flag=%-3s :: %s" % (v, m.strip()[:40]))
# 判据：文案出现【新的语义】才是分支线索
# ❌ 错误判据：出现「-操作过于频繁」就认定该值是分支 ⇒ 那只是账号级计数打到顶
```
**红线**：值域枚举/登录探测**必须每个探针换一个假账号**（计数键含账号参数值）；否则打满真实账号的桶会把唯一的活登录口锁死，且**冷却时间通常是分钟级**。
**为什么五步缺一不可**
| 只做 | 会得出 |
|---|---|
| 只发单参数 | **假否定**（掉进报错分支，判"不可写"） |
| 写后立刻读回 | **假否定**（命中缓存旧值，判"假写"） |
| 看限流判分支 | **假肯定**（把计数到顶误判成"该 flag 是真入口"） |
| 用真账号做值域 | **锁桶**（把唯一的活登录口打死） |
```
