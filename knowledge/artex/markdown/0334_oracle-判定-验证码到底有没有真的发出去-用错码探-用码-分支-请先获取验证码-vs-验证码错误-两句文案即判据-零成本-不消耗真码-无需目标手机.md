## 描述

★ 通用 oracle：判定「短信验证码到底有没有真的发出去」——**不需要目标手机、不用等短信、不消耗用户手上的真码**，一次请求出结果。

**为什么需要它**：短信通道有两种坏法 —— ①网关没调用（存根/桩）；②网关调用了但用户没收到（运营商/黑名单/信号）。**两种在外部完全无法区分**，于是团队会陷入"发了没有？再发一次？用户到底收到没？"的循环，还可能让用户为了等一条永远不来的短信干等几分钟。

**原理**：多数老系统的状态机顺序是「**先查该账号是否取过码 → 再校验码是否正确**」。所以"库里有没有码"这个**内部状态**会从**错误文案**里漏出来：
```
用错码（如 111111）打「用码」分支：
  「-请先获取验证码！」      ⇒ 库里【没有】码  ⇒ 发码通道是存根（发了也白发）
  「-验证码错误，修改失败！」⇒ 库里【有】码    ⇒ 通道是真的，可以叫用户去看手机
  「-操作过于频繁」          ⇒ 桶被限流，本次判定无效（等冷却再判）
```
**关键技巧**：用**错码**探 —— 它只触发"有没有码"的判断，**不会消耗/作废用户手上那条真码**。

**操作步骤**
```bash
# ① 先走一次发码（任一候选通道），记录时间
POST /LHService/register18  username=<账号>&flag=3        # 或其它候选发码档
# ② ★ 立刻用错码探「码是否入库」
POST /LHService/register18 \
  username=<账号>&password=Abc12345&name=rt58&yzm=111111&flag=4&registerLv=0&isReal=0
# ③ 读文案定论（见上面的三档判据）
```
**注意事项**
· **参数名要试对**：本靶标 `Register_phone` 读的是 `username` 而**不是** `phone` ⇒ 用 `phone=` 打会被忽略，于是"空号也回发送成功"，容易被误判成存根。**先用一个合法值 + 一个非法值对照，确认服务端真的读了这个参数名。**
· **别用真码探**（会作废）；**别用真账号连打**（限流键含账号，打满就把唯一的活登录口锁死）。
· **对照两条相邻文案就够**，不必穷举。
· 若发码返回的是千篇一律的「成功」文案，**不要相信它** —— 用本 oracle 验证。同理适用于「testpool 连接成功」「upload 更改成功」这类无条件假成功文案。

**本靶标实测结果**
```
发码档：Register_phone?flag=3「发送成功」与 register18?flag=1 的「发送成功」都曾在【空号码】上返回成功 ⇒ 存根
判据档：register18 flag=4 + 错码 111111
  全新假号（从未取码） -> 200/25B「-请先获取验证码！」   ✅ 与"库里没码"一致 ⇒ oracle 有效
真码用码档：register18 flag=2(注册) / flag=4(改密) 是唯二会走到码校验的分支
无用档：    flag=0 与 flag=5..11 全部 200/0B（空响应，不动作）⇒ 「换 flag 找登录档」这条路不存在
```

```python
def verify_code_arrived(acct):
    """零成本判定验证码是否真的入库；用错码探，不消耗用户手上的真码"""
    r = POST("/LHService/register18",
             "username=%s&password=Abc12345&name=rt58&yzm=111111&flag=4&registerLv=0&isReal=0" % acct)
    m = txt(r).strip()
    if "请先获取验证码" in m:
        return False          # ★ 库里没码 ⇒ 发码通道是存根，别让用户白等
    if "验证码错误" in m:
        return True           # ★★ 库里有码 ⇒ 通道是真的，可以叫用户看手机
    if "操作过于频繁" in m:
        return None           # 桶被限流，本次无效
    return None               # 未知文案，人工判读
```

**先做这一步（否则 oracle 会被自己误导）**
```python
# 确认服务端到底读的是哪个参数名 —— 用「合法值 vs 非法/空值」对照
POST(path, "flag=1&username=13000001111")   # 记文案 A
POST(path, "flag=1&username=")              # 记文案 B
POST(path, "flag=1&phone=13000001111")      # 记文案 C（若 C 与"完全没有号码参数"时相同 ⇒ phone 被忽略）
```
本靶标教训：`Register_phone` 读的是 **`username`**；用 `phone=` 打会被忽略 ⇒ "空号也回发送成功"被误判为存根。**参数名不对 ⇒ oracle 的结论也会错。**

**红线**
| 做法 | 后果 |
|---|---|
| 用用户手上的真码去探 | 码被作废 / 消耗 |
| 用真账号连打多轮 | 限流键含账号 ⇒ 打满桶，把唯一的活登录口锁死（冷却常为分钟级） |
| 相信「发送成功」文案 | 存根也会回成功 ⇒ 误判"已发码"而让用户干等 |
```
